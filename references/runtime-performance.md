# 运行性能与同步行为

2026-11-20：Gitowl 不再要求严格复用上游内核。采用方案及官方来源见 [调查记录](../third_party/performance-evaluation.md)。本轮保留当前 Electron 宿主和随包 Git，修改实际同步和刷新路径。

## 用户可见变化

- 普通获取、拉取和推送不再自动快进未检出的其他本地分支；远端跟踪分支仍按 Git 正常更新。
- 获取/拉取复用一次连接更新远端默认分支，不再额外连接查询 HEAD。
- 本地改动由文件通知触发；200 毫秒内通知合并，每 60 秒校准本地状态，每 5 分钟校准完整元数据。选中项目优先，操作占用时延后，监听失败记录日志并重试，恢复时完整校准。
- 分支保护资料异步刷新；同步结果不再等待该 API。保留身份和当前分支检查，防止迟到结果覆盖另一个选择。
- 同一帧状态变更合并推送，命令结果和交互请求仍独立返回。

## 测量方法

Windows x64，同一台机器、同一随包 Git、本地隔离远端、新建用户目录。每个版本获取、无新提交拉取、手动刷新各 5 次；记录中位数及全部样本。空闲观察 11 秒；修改文件后等待侧边栏真实计数更新。通过 Git Trace2 核对实际子进程和传输次数。

旧版本来自修改前已核验的生产运行时，输入摘要为 `fae987e9770b3a193ac2bfcff6dcc5fa25289522e5e03898cc8987d6eae3c283`。新版本使用本轮生产源码构建。网络、服务器传输、百万文件仓库及启动内存收益不能由这个本地样本推断。

## 实测结果

以下为完整回归结束后的低负载顺序测量，两版本各 5 次，取中位数。仍是本机观察，不是跨设备或远端网络的稳定性能保证。

| 操作 | 修改前 | 修改后 | 本机观察 |
| --- | ---: | ---: | --- |
| 获取 | 2,185 ms | 1,793 ms | 约减少 18% |
| 拉取，无新提交 | 3,752 ms | 3,410 ms | 约减少 9% |
| 手动刷新 | 1,142 ms | 1,110 ms | 约减少 3%，差异较小 |
| 上述 10 次同步的 Git 传输 | 20 次 | 10 次 | 每次同步省去一轮远端连接 |
| 文件修改到侧边栏计数更新，单次 | 2,761 ms | 347 ms | 通知触发替代等待轮询 |

原始样本（ms）：获取旧 `[2107,2060,2185,2261,2199]`、新 `[1838,1747,1675,1805,1793]`；拉取旧 `[3737,3849,3952,3752,3702]`、新 `[3613,3357,3410,3479,3364]`；刷新旧 `[1195,1083,1097,1142,1263]`、新 `[1180,1110,1096,1074,1114]`。

旧版空闲 11 秒启动 2 次 Git 状态读取、2 次状态推送；最终新版同样窗口中 0 次 Git 启动、1 次状态推送。先前独立空闲样本也观察到 0 次 Git 启动；初版顺序同步样本恰逢完整校准，记录了 22 次 Git 启动，因此进一步把每分钟校准改为本地状态读取，完整元数据校准降至每 5 分钟。不能把短窗口零扫描当作“空闲永远零开销”。

冷启动仅测一次：旧 1,965 ms、新 1,952 ms，基本相同，未证明启动提速。网络远端总耗时、内存和大型仓库上限尚未测量。此次确认的收益是少一轮连接、去掉附带分支更新与 API 等待、减少周期扫描和更快发现本地改动。

## 验证与限制

- 仓库回归 32 项通过；类型检查、修改文件 lint、来源与功能声明检查通过。
- 真实 Git 回归覆盖默认分支改变、显式逐远端配置不被覆盖、Git 配置文件不变、fetch 不改工作目录、pull 保留未提交文件及其他本地分支、子模块和保存后推送。
- 文件监听覆盖突发合并、扫描期间继续写入、占用延后、独立 worktree 元数据、移除项目、监视失败重试和关闭清理；快照合并覆盖最新状态及关闭后的取消。
- 生产 MyGo 五类集成检查及单实例回归通过。Go 主程序、编辑器和后端通过；Windows 调度测试先创建进程再降低优先级，避免夹具在启动阶段饿死，保留原恢复断言。
- 直接启动冒烟在并发重载时曾超时，诊断确认停在已应答关闭后的 Electron 退出；旧安装包同条件也复现。负载下降后原检查在 6.98 秒通过，最终源码重新构建后的检查在 3.07 秒通过，未放宽断言或跳过。
- 全套单元回归执行 3,983 项：首次 3,914 通过、29 失败（含子测试汇总）、40 条件跳过。临时空目录失败来自工作区内向上发现父仓库；复验设置 `GIT_CEILING_DIRECTORIES` 到本轮临时根目录后，相关 98 项、差异展开 8 项及严格状态错误 1 项全部通过。新增同步等待测试在重载下触及原 10 秒上限，改用 60 秒作为死锁检测界限；资料请求始终不释放，仍要求同步自行完成。
- 辅助提交故障探针原假定 `fetch` 位于参数首位；现跳过命令级 `-c` 参数，继续在真实 fetch 完成后注入故障，原数据保护断言保留。受影响的 18 项边界测试复验全部通过。
- 初次另有两个夹具目录重命名遇到 Windows `EPERM`，分别是部分行恢复与重命名识别；原断言定向复验通过，未改相关产品代码。
- 最后一次校准调整只涉及 watcher；相关 13 项回归全部通过，包含每分钟轻量读取、第五次完整读取和监视故障恢复。

上述结果是完整回归加定向复验，不表示把首次失败报告改写成全绿。固定安装器另校验当前暂存源码树和 SHA-256。本轮使用隔离测试数据，没有安装、升级或卸载用户已安装的 Gitowl。

## 2026-11-22 内存

任务管理器显示的“内存”是私有工作集。已安装版本空闲时：MyGo 界面进程约 59 MB，Node 后台约 106 MB，合计约 165 MB。主要占用在 Node 后台。

| 原因 | 处理 | 本机结果 |
| --- | --- | --- |
| V8 保留已加载 chunk 的源码；7.6 MB 和 3.7 MB 两个 chunk 只含约 2,800 个非 ASCII 字符，却整体按 UTF-16 存储，约 22 MB | Node 后台 bundle 只重新输出：转义非 ASCII、删除注释；不压缩、不改名 | 空项目后台 RSS 中位数 105 → 87 MB，V8 堆 45 → 28 MB |
| 主线程同时加载 ImageMagick/UPNG 模块，实际只有解码线程使用 | 非 Node 宿主才动态加载 | 主线程不再加载这些模块 |
| 查看一次图片后解码线程常驻，约 60 MB | 60 秒没有请求后停止；下一张图片重新启动 | 单独测量：解码后 117 MB，停止后 56 MB |

测量方法：使用组装后的 `output/native-runtime/backend/`、新建测试资料、空闲 15 秒，每个版本 3 次。没有用真实项目复测；含项目、历史和 Copilot 的峰值不能由此推断。

## 2026-11-25 基础安装内容

对照来源与可借鉴实现见 [51code 调查](../third_party/51code-lightweight-evaluation.md)。用户选择将 Copilot 原生组件改为首次使用下载，保留完整官方 SDK 平台包及校验。Git、SSH、LFS、凭据 helper、数据库和图像功能继续随基础包提供。

基线为 `abeebe7945` 的已核验后台目录；同一 Windows x64 环境，对实际运行目录逐文件累计长度，单位 MiB（1,048,576 字节），不按源码行数推算。

| 项目 | 修改前 | 修改后 |

验证覆盖：真实 HTTP/归档、完整性失败、文件损坏、并发请求、取消与重试、重启离线复用、官方平台包 SDK 启动；基础包启动、SQLite、图像像素、网络代理、真实 Git 及 MyGo 集成。简繁英、深浅主题和最小窗口控件回归另行核对。过程发现设置对话框新增进度条会挤压原页脚，已按真实控件高度纳入布局测量并复验。
